# Добавление детали в остаток сохранённой карты

2026-11-07. Пользователь получил 187 деталей на 16 листах с остатком 2730×375 мм, затем добавил одну деталь 2700×370 и получил 17 листов. Геометрически эта деталь помещается: `370 + 5 = 375`, `2700 + 5 + 25 = 2730`.

## Причина в конвейере

Быстрая фаза опыта принимала только полное точное совпадение заказа. После добавления детали прежняя книга переставала быть полным совпадением и пропускалась. В более позднем поиске оставшиеся детали отправлялись в отдельный подзаказ с добавлением его листов; свободные участки сохранённых полос перед этим не заполнялись. Увеличение времени общего поиска не заменяло этот пропущенный шаг.

## Общее исправление

`src/completed-rip-recovery.js` не содержит размеров заказа, номеров деталей или заранее заданных координат. Он:

1. Связывает реальные детали из сохранённой книги с текущим заказом по размерам и разрешённой ориентации, не превышая количества каждой строки.
2. Восстанавливает и независимо проверяет прежнюю схему для уже размещённого подмножества.
3. Перебирает настоящие терминальные прямоугольники отхода; размеры для проверки ограничиваются полезной областью листа после обрезки.
4. Строит кандидата локального гильотинного раскроя, затем заново компилирует и воспроизводит весь физический план. Проверяются сохранение прежней геометрии и положение новой детали внутри выбранного свободного прямоугольника.
5. Публикует карту только после размещения всего текущего заказа. Частичное заполнение может использоваться внутренним поиском опыта; оставшиеся детали рассчитываются отдельно только после попытки заполнить существующие листы.

Worker выполняет эту фазу до нового полного перебора и native-поиска. Более новая книга на 17 листов не скрывает старую книгу на 16: сначала рассматриваются книги с меньшим числом листов. Непригодность одного локального варианта не объявляется невозможностью раскроя вообще.

Ранняя фаза ограничена 5 с; по умолчанию рассматривается не более 64 добавленных экземпляров и 128 проб на книгу. Это ограниченный последовательный поиск по существующим свободным прямоугольникам; он не доказывает оптимальность сложных перестановок. Общий поиск остаётся доступным после него. Технологический профиль и независимый валидатор не ослаблялись.

Изменено удержание книг в опыте: до четырёх вариантов на один точный состав размеров/количеств, с предпочтением меньшего числа листов; общий предел 16 книг / 6 MiB сохранён. Это предотвращает вытеснение исходного заказа множеством вариантов одного следующего заказа. Формат version=1 остаётся совместимым. Уже утраченная книга не восстанавливается из отсутствующих данных — её можно явно импортировать из проверенного JSON.

## Сквозная проверка реального сценария

В отдельную пустую базу импортирована **только исходная карта на 187 деталей**. Через обычный HTTP API выполнены два запроса: старый заказ, затем тот же заказ с 2700×370. Результат:

- Было: 187 деталей, 16 листов, 446 резов, 149 поворотов после серверной сортировки.
- Стало: **188 деталей, 16 листов, 450 резов, 151 поворот**.
- Добавленная деталь: лист 16, `X=10, Y=1445`, размер 2700×370; геометрия прежних размещений сохранена.
- Время второго HTTP-запроса в повторном локальном испытании — около **277 мс**.
- Ни одной native-попытки или нового общего раскроя; `learningMove=stored-waste-fill`, добавлена одна деталь, полный результат сохранён в опыт.

Отдельно проверен упакованный runtime-release с базой только на 187 деталей: worker воспроизвёл 188 деталей на 16 листах примерно за 226 мс, без native-попыток. Время относится к локальной среде, не к измерению VPS.

Карты, PDF, физические операции и оба результата API: [order-188-remnant](../benchmarks/order-188-remnant/RESULTS.md).

## Проверки

Девять новых регрессий: настоящий заказ 187+1, более новая 17-листовая книга, заполнение до выделения нового листа, соблюдение текстуры, запрет публикации частичной карты, уникальные номера экземпляров при объединении с остаточным подзаказом, границы обрезки, остановка по бюджету и сохранение исходной книги при большом числе вариантов следующего заказа.

Из `listpro-core/`:

```sh
node --test tests/completed-rip-recovery.test.js tests/completed-rip.test.js
node server/scripts/benchmark-added-part.cjs /tmp/added-part-api
node benchmarks/order-188-remnant/verify.cjs
CHROMIUM_PATH=/usr/bin/chromium node benchmarks/order-188-remnant/render-pdf.cjs
npm test
npm run benchmark
```

После установки `/healthz` содержит `storedWasteRecovery:true`. Для обновления существующего VPS используется `server/scripts/update.sh`; опционально можно явно импортировать прежнюю карту `order-187-target16/result.json`. Тогда именно алгоритм заполнит остаток новой деталью при следующем запросе, без подстановки готовой 188-детальной карты. База, пароль и существующая конфигурация HTTPS сохраняются установщиком.

Итоги: `npm test` — **10119 пройдено, 0 ошибок**; локальный `npm run benchmark` пройден (архивное внешнее сравнение только для CI/явного флага не запускалось). Проверено заполнение в упакованном runtime-release: 187 → 188 деталей на тех же 16 листах без native-поиска. PDF: 16 страниц; все 1385 кадров отрисованы без ошибок JavaScript. На рабочий VPS изменения из этой среды не устанавливались.

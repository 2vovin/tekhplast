# ЛистПро Brain 2.0 — рекурсивный полосный эксперимент

## Результат на исправленном заказе

Все 26 экземпляров размещены на **одном листе**, без поворота деталей относительно текстуры. Найдены варианты с **41 физическим пропилом**, включая подрезку краёв. Исходные параметры взяты из неизменённого [bazis-26-corrected.json](../benchmarks/bazis-26-corrected.json): 2750×1830, керф 5, обрезка 10 мм; позиция 4 — 238×180, пять экземпляров. Керф/обрезка сохраняют статус предположений предыдущего экзамена относительно реальной карты БАЗИС.

Первые две строки — существующие проверенные артефакты, а не новые запуски на изменённом заказе. Сравнение времени повторного запуска старого поиска и нового ядра на одном CI-хосте записывается отдельно.

Вариант «баланс» сокращает число пропилов относительно 44 на 3 (6,82%), длину на 2134 мм, общее число операций на 4 и увеличивает крупнейший остаток до **310×773 мм**. Цена — два дополнительных поворота и увеличение глубины с 7 до 9. Вариант с 15 поворотами имеет меньший остаток **187×398 мм**. Вариант с **44 резами и 13 поворотами** использует те же первичные ширины 297 и 2418 мм, что прежний расширенный PSS. При равном числе резов он сокращает длину на 716 мм, число поворотов/операций на один, глубину с 7 до 5 и увеличивает крупнейший остаток с 89100 до **128940 мм² (420×307)**. Он улучшает прежний 44-резовый результат по всем остальным перечисленным показателям. Однако единого победителя по всем критериям среди всего архива, включая строгий 48-резовый вариант, нет.

Фиксированный рейтинг ядра: минимум листов → максимум площади одного отдельного остатка → резы → повороты → все операции → длина. Поэтому автоматический incumbent — вариант с остатком **1145×230 мм**, 45 резами. Более дешёвые варианты сохраняются в Pareto-архиве, а не заменяются этим incumbent. Удаление альтернатив при улучшении числа листов не позволяет пустому второму листу выиграть за счёт размера остатка. Полезность остатка здесь — геометрический показатель; пороги склада и стоимость повторного использования не заданы.

Три варианта с 41/45 резами используют одну **физически отделённую** рабочую полосу 2720×1830 мм, которая затем торцуется до 2720×1810. После боковых подрезок у сырой плиты остаётся 2730 мм; первичный рез отделяет полосу 2720 мм, расходует 5 мм керфа и оставляет **5×1830 мм основной остаток**. Он остаётся отходом, никогда не вращается и не становится полосой через endPrimary. Внутри рабочей полосы каждый поперечный или продольный рез относится к уже существующему меньшему blankId.

Ширина 2720 не обосновывается фиктивной составной деталью-якорем. Это отдельная модель полностью отделяемых полос из актуального RECURSIVE-STRIP-RESEARCH.md, разрешённая также предыдущим расширенным экзаменом. Старый якорный PSS оставлен неизменным. Возможность реально удержать такой остаток, повернуть столь широкую полосу и выполнить все подачи конкретным центром **не установлена**.

Статусы независимой проверки:
- geometryValid = true;
- abstractCutPlanValid = true (также сохранён совместимый abstractStagedValid);
- machineFeasibility = unknown.

Профиль: abstract-staged-detached-strips-exam-v1, PANEL_SAW_STAGED, машинная ось V, исходный лист без поворота, каждая отделённая заготовка максимум один поворот. Неизвестны ограничения глубины, захватов, подачи и минимального удерживаемого остатка. Установка конечных ограничений в профиле проверяется и может отклонить эти карты. Подтверждения станочной совместимости, сертификата ЧПУ и доказательства минимального числа резов нет. Для этого конкретного непустого заказа один лист достигает тривиальной нижней границы по числу листов; остальные критерии остаются эвристическими.

## Самостоятельное ядро

Новые файлы: src/recursive-strip.js, recursive-strip-validator.js, recursive-strip-cases.js, recursive-strip-artifacts.js. Код прежних оптимизаторов не изменён и не вызывается новым поиском. Использованы существующие общие средства проверки входа, сбора дерева, компиляции физических операций и независимого replay. Старое ядро вызывается только отдельным сравнительным benchmark.

1. Группирование по точным размерам, флагу текстуры и texture. Настоящие id/instance сохраняются; равные размеры не сливают номера заказных позиций.
2. Для каждого рекурсивного прямоугольника выбирается направление полосы и семейство M(δ). Варьируются δ = 0; 0,05; 0,1; 0,2; 0,5; 0,99, приоритеты семейств, порядок деталей и число/порядок первичных полос. δ влияет только на выбор кандидатов, **никогда на размеры**.
3. Размещение вдоль полосы решается sparse 0/1 DP либо жадной линейной эвристикой с различными приоритетами. Керф включён между экземплярами; непустой торцевой зазор должен допускать настоящий рез. Оба варианта входят в портфель поиска.
4. Каждый отрезанный сегмент с деталью имеет собственный прямоугольный остаток; свободные участки внутри полосы, её хвост и соседние подполосы обрабатываются рекурсивно с общим остатком спроса.
5. Первичные полосы комбинируются по ширине: одиночная широкая отделённая полоса, размерные полосы с широким дополнением, либо 1D DP по оценкам семейств. DP-композиция является эвристической: оценённая ценность полос меняется после расходования экземпляров в других полосах. Полученная реальная карта всё равно проверяется полностью.
6. На каждом принятом улучшении onBest получает независимо проверенную копию. CLI атомарно сохраняет её через временный файл и rename. previous позволяет продолжать поиск с предварительной повторной валидацией incumbent. Неисправный incumbent отклоняется.
7. Pareto-архив удерживает недоминируемые варианты минимального найденного числа листов по остатку, резам, поворотам, операциям и длине.

Точный DP относится только к конечной линейной подзадаче с зафиксированными кандидатами/весами, когда exact=true. При превышении 20000 состояний включается явно отмеченная эвристическая отсечка; prunedDP считает такие вызовы заполнения. В контрольном поиске отсечек не было. Приведён независимый полный перебор 256 подмножеств для 100 небольших тестов DP. Глобальный multistart, семейные приоритеты, выбор осей, рекурсия и композиция полос не являются точным решателем всей двумерной задачи. Branch-and-bound и LNS в этом новом ядре не заявлены.

Начальный эксперимент: seed=2026, 20000 итераций; 592753 рассмотренных рекурсивных прямоугольника, 52346 DP-вызовов заполнения, 360736 накопленных конечных DP-состояний, 2136 вызовов первичной DP-композиции; 299 карт прошли физическую проверку перед рассмотрением для сохранения. Карты с уже худшим числом листов отбрасываются после геометрической проверки. Поиск с нуля, без подстановки прежних раскладок.

Чувствительность δ в этом портфеле: минимальное число листов равно 1 для всех шести значений. Минимум геометрических резов среди однолистовых кандидатов: соответственно 39, 38, 37, 38, 38, 38. Это не физические итоги с подрезками и не контролируемый эксперимент единственного фактора: δ чередуется с другими стратегиями. Нельзя переносить эти цифры на другие заказы или объявлять одно δ универсально лучшим.

Ограничения реализации: целочисленные миллиметры, положительный керф, trim=0 либо trim≥kerf; первичная ось V; положительный конечный остаток зарезервирован. Из-за последнего ограничения детали почти во всю ширину листа могут не получить решения. Ошибка «не найдено в модели/бюджете» не означает невозможности. FORMAT_SAW сохраняется в старом отдельном модуле; новое API не выдаёт staged-проверку за результат FORMAT_SAW.

## Публикации и PackingSolver

[Бунаков, 2007](https://sapr.ru/article/18388): использована опубликованная идея семейств близких главных размеров, линейного заполнения полос, рекурсивной обработки их остатков и последующей композиции. Это независимая реализация исследовательского принципа, не копия закрытого БАЗИС и не утверждение о внутреннем коде БАЗИС 10.

[Бунаков, 2021](https://sapr.ru/article/26269): настройка порядка подрезки и приоритетов зависит от оборудования. Здесь применена явная подрезка отделённых полос и раздельные показатели трудоёмкости. Стоимость времени работы не калибрована: число CUT/ROTATE/FEED служит измеримым описанием, а не оценкой секунд станочного цикла.

[PackingSolver](https://github.com/fontanf/packingsolver), [документация](https://fontanf.github.io/packingsolver/rectangleguillotine.html): модуль rectangleguillotine поддерживает направление первой стадии, ограниченные/неограниченные стадии, керф, подрезки и запрет вращения деталей. Выполняется как внешний бинарный benchmark, библиотека в ядро не включена. MIT-уведомление сохранено в PACKINGSOLVER-LICENSE.txt.

Фиксация внешнего исполняемого файла:
- upstream commit bc1741241ea21d1e3c10c56cab95381947a864e7;
- Linux x64 release asset 704885214;
- SHA256 39596b817c638dc69af04e007ded4d3949fda8cd1adf17a902f16a3b044d8ab5.

Перед запуском проверяется SHA256. Если подвижный release latest изменится, benchmark откажется выполнять неподтверждённый бинарник; обновление версии должно быть отдельным проверяемым изменением. Автоматической подмены версии нет.

Внешние условия: тот же заказ, hard trim 10 с четырёх сторон, kerf 5, вертикальная первая стадия, unlimited stages, cut_type non-exact, objective bin-packing-with-leftovers; oriented задаётся отдельно каждой позиции. Внешний алгоритм не обязан сохранять наш положительный основной остаток или описывать физические повороты. Поэтому его число листов/геометрия сопоставимы как ориентир, но число узлов CSV нельзя называть числом PSS-пропилов. Собственная проверка внешнего CSV контролирует размеры, количества, текстуру, границы и керф; abstractCutPlanValid=null, machineFeasibility=unknown до полноценного преобразования в CUT/ROTATE/FEED.

## Воспроизведение и испытания

Из listpro-core/:

~~~sh
npm test
npm run benchmark
npm run benchmark:brain2
BRAIN2_EXTERNAL=1 npm run benchmark:brain2
~~~

BRAIN2_OUTPUT задаёт папку новых результатов; по умолчанию используется временная папка listpro-brain2-results. Основной benchmark автоматически вызывает новый опыт после всех исторических регрессий. В CI внешний benchmark запускается автоматически. Загружается только открытый проверенный бинарник PackingSolver. На одноразовом GitHub runner при необходимости устанавливаются liblapack3, libblas3 и libgfortran5 из системного репозитория. Локально зависимости устанавливает оператор; скрипт не вызывает sudo вне GitHub Actions.

Данные дополнительных 10 заказов и контрольного — benchmarks/brain2/cases.json, генератор src/recursive-strip-cases.js, seed набора 20026. Варианты: удвоенный исправленный заказ 52; разнообразные 30/50/100/200; узкие 60; квадраты 80; повторяющиеся малые 200; разрешённые повороты 50; смешанные флаги текстуры 65. Новое ядро и предыдущий расширенный PSS получают seed=2026 и 20000/100 итераций на контрольном/остальных заказах. Внешний PackingSolver получает 20/3 секунды; это фиксированные бюджеты разных алгоритмов, не равенство объёма работы или доказательство сравнительного быстродействия.

Добавлены 1000 случайных заказов с независимым replay, 100 сравнений DP с полным перебором, контрольные и отрицательные тесты: поддельная полоса, основной остаток, двойной поворот, новые счётчики, повторное использование ID, текстура, керф, неполный состав, сквозной рез через связанную деталь, ошибочная длина хода, неизвестная станочная совместимость. Отдельно проверяется внешний CSV.

Начальное состояние ветки 940fa0a93888f063e50638239c80202f40bee713 имеет успешный GitHub Actions run 41647406381. Локальная командная среда этой сессии не запустилась; предварительные новые тесты выполнены в JS-окружении инструментов.
